# 编码与提交约定

这份约定用于控制新增和修改代码的风格，不要求为了统一外观而一次性格式化历史文件。
功能改动之外的大范围格式化应单独提交。

## 通用原则

- 先沿用所在文件的排版和命名，再考虑全局统一。
- 一个函数只承担一个可以说清楚的职责；复杂条件优先提取为有名字的规则。
- 错误信息要包含失败对象和下一步线索，避免只写“失败”或“异常”。
- 不吞掉异常，不用空 `catch` 和无说明的兜底值掩盖协议或现场问题。
- 新增行为应有相应测试；无法自动化时，记录可复现的人工验证证据。

## 注释

项目自有代码的新增注释使用自然、简洁的中文。协议名、类名、标准术语和上游 API 不必
强行翻译。

注释重点说明：

- 为什么采用这个处理方式；
- 协议字段、单位、方向、频率和兼容限制；
- 线程所有权、对象生命周期和容易踩到的时序条件；
- 现场行为与普通桌面软件不同的原因；
- 暂时保留兼容代码的删除条件。

避免这些写法：

- 把代码逐句翻译成注释；
- “初始化变量”“进入循环”这类没有额外信息的说明；
- “临时修一下”“后面优化”等没有责任边界和删除条件的 TODO；
- 过度整齐、重复结论、像自动生成说明书一样的长段注释。

示例：

```cpp
// 切换机器人后旧连接仍可能返回结果，用会话编号丢弃迟到回调。
if (sessionId != m_activeSessionId) {
  return;
}
```

## C++ 与 Qt

- 使用 C++17 和 Qt 6。
- 类型使用 `PascalCase`，函数和局部变量使用 `camelCase`，成员变量使用 `m_` 前缀。
- QObject 优先通过 parent 管理所有权；跨线程对象必须写清创建、使用和销毁线程。
- 信号描述已经发生的事实，槽和 action 描述要执行的动作。
- UI 线程不等待网络连接、消息投递、视频解码或长时间线程退出。
- Protobuf 只通过生成类型序列化和解析，不在业务代码中手写等价字节布局。
- 新增头文件只暴露调用方真正需要的类型，能用前置声明时避免扩大公共依赖。

现有 C++ 文件主要使用两个空格缩进，`.editorconfig` 对新增内容采用相同设置。

## Python 模拟器与工具

- Python 代码使用四个空格缩进，公开函数尽量提供类型提示。
- 模块导入不连接网络、不启动线程、不解析进程级参数。
- 业务规则与 FastAPI、Socket.IO、MQTT、UDP 适配器分开测试。
- 外部输入先校验再进入状态层；测试中使用 fake clock、fake transport 和固定随机种子。
- 脚本返回码要能区分成功、验证失败和环境缺失。

## QML 与 JavaScript

- QML 负责展示和交互，不解释 Protobuf，也不保存 Broker、端口等 transport 配置。
- 复用 `GameData` 投影和有类型 action，避免多个页面复制同一比赛状态语义。
- 布局修改至少检查常用分辨率、1.25/1.5/2.0 缩放和红蓝方视角。
- 高频动画和 Canvas 绘制要避免在每帧创建无界对象或打印日志。

## 提交习惯

提交信息使用简短中文，写清这次提交完成的动作。推荐格式：

```text
<type>: <简短说明>
```

常用类型：

- `feat`：新增用户可见能力；
- `fix`：修复缺陷或安全边界；
- `refactor`：行为不变的内部整理；
- `test`：新增或修正测试；
- `docs`：文档；
- `build`：CMake、依赖和构建；
- `chore`：仓库卫生或维护工作。

合适的例子：

```text
fix: 收紧现场场景动作授权
build: 隔离开发观测依赖
docs: 补充模拟器启动说明
```

一个提交只解决一个主题。不要混入个人配置、运行日志、生成文件和无关格式化；提交说明
记录问题和结果，不需要描述使用了哪一种开发辅助工具。

## 变更前后检查

```bash
git diff --check
cmake --build --preset dev
ctest --preset dev
python3 tools/release/check_public_readiness.py
```

根据改动范围追加协议、模拟器、QML 或运行时验证，完整矩阵见
[测试与质量门](../architecture/testing.md)。
