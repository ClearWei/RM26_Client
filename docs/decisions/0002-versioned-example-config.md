# ADR 0002：只跟踪公开示例配置

- 状态：accepted
- 日期：2026-08-21
- 复核日期：2026-08-25
- 决策人：RM26 客户端维护团队

## 背景

早期工程直接跟踪根目录 `config.json`，CMake、Docker 和现场脚本也都依赖这个文件。这样虽然方便，
但现场地址、机器人身份和本地素材路径很容易随源码提交。公开模板与真实运行配置必须分开，同时又
不能让干净克隆因为缺少本地文件而无法构建。

## 决策

仓库只跟踪 `config.example.json`，本地 `config.json` 由 Git 和 Docker 构建上下文忽略。示例只使用
回环地址和中性身份，不包含凭据或个人路径，并由发布检查和日常 CI 保护。

CMake 配置时优先使用本地 `config.json`；文件不存在时使用 `config.example.json`，并在构建目录和
可执行文件旁生成名为 `config.json` 的运行副本。因此干净克隆可以直接构建，现场配置仍能保持原有
加载路径。Docker 镜像只编入示例配置，真实配置在容器启动时只读挂载。

## 结果

正面影响：

- 新贡献者得到稳定、脱敏且能独立检查的配置入口。
- 公开发布预检可以基于 Git 索引判断示例是否安全。
- 干净克隆和公开源码包不依赖未提交文件即可完成构建。
- Docker 镜像不会因为本机存在配置而把现场参数写入镜像层。

代价：

- 本地配置不会自动获得模板新增字段，升级后需要对照说明主动同步。
- 运行配置、普通启动脚本和模拟器已采用回环默认值；现场入口缺少显式配置时会直接退出。
- 示例检查保护公开模板，不替代真实网络和设备联调。

## 备选方案

### 继续只跟踪运行配置

未采用。它不能稳定区分公开默认值和现场值，也无法给首次使用者安全的复制入口。

### 继续同时跟踪示例和运行配置

未采用。两份文件一旦出现字段或现场值差异，维护者很难判断哪一份可以公开，也无法阻止真实参数
进入提交历史或 Docker 镜像。

## 重新评估条件

如果未来引入配置生成器、系统级配置目录或密钥管理服务，应重新评估文件位置和优先级；无论采用
哪种方式，公开源码包都不能依赖真实现场配置才能构建。
