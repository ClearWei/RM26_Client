# 传输接入与链路诊断

本文说明协议语义、传输方式和现场部署之间的边界，并给出 MQTT、视频与渲染问题的定位方法。
它不保存任何现场地址、账号、密钥或比赛日志。

## 三层边界

### 协议语义

协议语义回答“传什么”：消息名称、字段、方向、参数含义和频率限制。项目以
[官方资料索引](../references/official-materials.md)中的当赛季通信协议为外部依据，以
[`robomaster.proto`](../../src/network/proto/robomaster.proto)作为仓库内 canonical schema。

传输方式发生变化时，不应顺手修改 topic 或字段含义。协议调整也不能只靠某次现场抓包反推，
必须说明官方版本、兼容影响和验证证据。

### 传输接入

传输接入回答“怎么到达进程”：

| 路径 | 当前用途 | 边界 |
| --- | --- | --- |
| MQTT | 比赛状态下行和类型化命令上行 | 地址、端口和机器人身份来自配置，不写死在页面或协议类中 |
| UDP 图传 | 主 HEVC 视频接收 | 收包成功不代表组帧、解码和渲染均成功 |
| `CustomByteBlock` | 自定义状态和 H.264 视频负载 | 必须按 payload 结构分流，不把视频原文写入普通状态日志 |
| S1 或其他兼容入口 | 特定部署下的适配路径 | 只解决接入问题，不成为协议字段的第二套定义 |
| 独立模拟器 | 本地 MQTT、UDP 和视频协议对端 | 不进入生产客户端进程，也不替代官方协议 |

端口、Broker、机器人 ID 和视频参数的公开配置方式见
[配置说明](../getting-started/configuration.md)。全新克隆应从 `config.example.json` 生成本地配置，
现场值只放在被 Git 忽略的 `config.json`、环境变量或本地 profile 中。

### 部署环境

部署环境回答“这次在哪里运行”：引擎版本、客户端构建、网卡、Broker、白名单、防火墙、视频
编码和日志来源。它随场地和赛事软件变化，不属于仓库的长期事实。

建议每次联调单独记录：

| 项目 | 需要确认的内容 |
| --- | --- |
| 赛事端 | 软件版本、绑定网卡、实际发送接口 |
| 官方客户端 | 软件版本、是否与赛事端同机、可用日志 |
| 自定义客户端 | 提交、构建类型、运行主机、机器人身份 |
| MQTT | Broker 来源、端口、Client ID 规则、订阅是否成功 |
| 视频 | 目标地址、端口、编码、分辨率和帧率 |
| 采集条件 | 两端时钟、抓包网卡、起止时间和日志范围 |

公开报告只保留必要的版本、角色名和统计结果；现场 IP、主机名、账号、密钥文件名、原始抓包
和未授权日志不进入仓库。

## 先按阶段定位问题

诊断时按以下阶段记录链路状态，避免用一个“通或不通”概括整条链路：

| 阶段 | 可用证据 |
| --- | --- |
| 赛事端产生状态或视频 | 赛事端日志、发送端抓包 |
| MQTT Broker 收到并转发 | Broker 日志、同 Broker 被动订阅 |
| 自定义客户端收到 MQTT | `RM26_MQTT_RX_TIMING`、状态快照 |
| UDP 到达客户端主机 | 接收端抓包或 UDP tap |
| 分片组装完成 | 帧汇总、gap 和 timeout 统计 |
| 解码完成 | `RM26_VIDEO_FRAME_TIMING stage=decode` |
| Qt 完成绘制 | `RM26_VIDEO_FRAME_TIMING stage=render` |
| 上行命令进入发布接口 | `RM26_COMMAND_TIMING direction=tx` |
| 机器人最终执行 | 机器人或赛事端回执、带关联 ID 的日志 |

没有某一段的证据时，应写“未观测”或 `UNKNOWN`，不要因为下游有画面、上游端口可连接，
就推断中间每一段都已经通过。

## 客户端结构化日志

客户端默认把运行日志写入 `tmp/runtime_<timestamp>/runtime.log`。需要固定路径时设置：

```bash
export RM_RUNTIME_LOG_PATH=/path/to/runtime.log
```

默认只把 warning 和 critical 同步到终端。如需同时查看普通日志，可设置：

```bash
export RM_RUNTIME_LOG_STDERR=1
```

逐帧详细日志会明显增加输出量，只在短时间诊断时启用：

```bash
export RM_VERBOSE_VIDEO_LOG=1
```

关键事件及其用途：

| 事件 | 用途 |
| --- | --- |
| `RM26_MQTT_RX_TIMING` | 确认 topic 到达客户端进程的本地时刻 |
| `RM26_COMMAND_TIMING` | 观察 publish 调用、入队和可选等待时间 |
| `RM26_VIDEO_FRAME_SUMMARY` | 查看帧分片、连续性和丢弃摘要 |
| `RM26_VIDEO_FRAME_TIMING stage=decode` | 区分收包、组帧和解码耗时 |
| `RM26_VIDEO_FRAME_TIMING stage=render` | 观察解码完成到界面绘制的尾段耗时 |
| `RM26_VIDEO_STALL` | 区分接收、解码或渲染停滞 |

只有客户端本地时间戳时，`publish` 耗时不能写成机器人执行延迟，MQTT 收包时刻也不能写成
赛事端到客户端的端到端延迟。精确比较需要发送端和接收端共享帧 ID、序号或可对齐时间戳。

## 记录和分析链路证据

客户端会在显式启用诊断日志后输出上述结构化事件。分析时应保留原始日志、启动参数、版本和
采集时间；需要判断网络链路时，再配合 Wireshark 或 `tcpdump` 采集发送端与接收端数据。
未提供赛事端、机器人或官方客户端日志时，对应进程内部阶段应保持 `UNKNOWN`，不能从单端
日志外推完整链路结论。

## 常见现象的定位顺序

| 现象 | 优先检查 |
| --- | --- |
| Broker 上没有目标 topic | 赛事端发布、Broker 配置、网络路径 |
| Broker 有消息，客户端状态不变 | 订阅、Client ID、payload 解析、`GameData` 更新 |
| UDP 抓包没有数据 | 发送目标、网卡、防火墙和端口 |
| UDP 有数据，组帧数不增加 | 端口绑定、帧头、分片缺失和超时 |
| 组帧增加，解码数不增加 | 编码格式、关键帧、码流连续性和解码器状态 |
| 解码增加，界面没有新帧 | Qt 线程、帧率控制、页面可见性和绘制路径 |
| 画面可见但掉帧持续增加 | 解码吞吐、UI 主线程、缩放与丢旧帧策略 |
| 上行 publish 成功但没有执行 | 身份、命令参数、限频、赛事端接收和机器人回执 |

## 双端采集原则

需要判断丢包位置或端到端时延时，至少同时采集发送端和自定义客户端端：

1. 发送端抓包作为“实际发出”的基准。
2. 接收端抓包确认到达数量和时序。
3. 客户端结构化日志区分组帧、解码和渲染。
4. 用共同帧 ID、序号或时间窗口对齐，不按文件行号硬配对。
5. 官方客户端日志可以提供参照，但不能替代发送端与接收端证据。

执行远程采集前应确认目标、权限和现场影响；本地命令不得写入真实地址或账号，也不能在未经
授权时主动连接赛事环境。公开问题报告只提交脱敏后的统计和必要片段，不提交完整现场抓包。

更完整的协议链路见[组件职责与数据流](data-flow.md)，线程退出和重连约束见
[线程与对象生命周期](threading-model.md)。
